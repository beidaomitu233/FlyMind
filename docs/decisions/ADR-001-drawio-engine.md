# ADR 001 采用 draw.io 作为绘图引擎

日期：2026-10-16。状态：路线已确定，迁移待实施。决定来源：用户明确要求“使用 draw.io”，并要求完整 PRD 和技术文档。

## 背景

FlyMind 已有五类图形、MCP、SQLite 和自研画布。多次迭代仍需投入大量精力维护拖拽、线路、文字、容器和排版。产品的主要价值是 AI 生成高质量可用图形，维护完整白板分散了投入。

上级 PM Runtime 之前接入过 draw.io，但与后续 FlyMind 的模型、数据和技术栈不同。可以复用资源和接入经验，不能直接覆盖当前应用。

## 决定

2026-10-17 用户明确纠偏：替换的是底层绘图区/引擎，不是重做应用工作台。接入前的侧栏、分组/回收站、标题、工具栏、属性、新建和导出交互继续作为产品基线。NativeStudio独立技术试验壳不作为正式交付；原生画布嵌入原工作台，通过适配器接已有产品操作，不能用draw.io菜单替代全部FlyMind能力。本次先完成可实际操作的创建、编辑保存、导出小批次，不以完整后续路线为前置条件。

1. 使用 draw.io 完整编辑器替换自研绘图区，优先自托管 iframe 嵌入。
2. FlyMind 保留内容层、渲染策略、绘图标准、AI 质量评测、MCP、工作区和 SQLite。
3. AI 普通输入继续使用纯业务 JSON；坐标、大小、字体和走线由渲染层与引擎处理。
4. 原生文档保存在渲染层，建立稳定语义绑定和双向投影。用户编辑后的内容必须能被 AI 再次读取。
5. 前端与后台导出使用同一引擎资源和配置；不长期维护另一套自研渲染结果。
6. 先以 PBS 复杂泳道验证完整业务链路，通过后分批迁移五类图形和存量数据。

## 选择依据

draw.io 提供完整编辑器、正式业务图形和嵌入协议，符合减少编辑器维护的目标。[官方仓库](https://github.com/jgraph/drawio)、[集成文档](https://www.drawio.com/docs/reference/embed-mode/)

Drawnix、Excalidraw 保留为研究记录。X6、LogicFlow 更偏编辑框架，仍需要维护较多上层编辑功能；本次不采用多引擎按图形类型分流，避免增加同步与导出成本。

## 责任划分

| FlyMind 继续负责 | draw.io 承担 |
|---|---|
| 图形要表达的业务、内容校验和修改准确性 | 原生画布、选择、拖拽、缩放和基础编辑 |
| 图形模板与业务布局策略 | 图形绘制、连接、文字及线路交互 |
| 内容/渲染映射、版本与冲突 | 原生文档及编辑历史机制 |
| 存储、分组、回收站、MCP 与制品管理 | 同一引擎的显示和导出能力 |

引擎不能替代业务正确性、标准或复杂图的模板策略。迁移也不是简单用 iframe 替换 SVG：双向同步、AI 增量修改和无前端导出是必要交付。

## 已知约束

- 本地资源版本与在线文档能力可能不同，先固定版本再验收。
- 代码、图形资源、第三方库和浏览器分发条件分别核查。
- 官方 Docker 当前说明存在评估/生产区分，旧独立导出镜像已停止维护，不沿用旧教程作为架构前提。[Docker 仓库](https://github.com/jgraph/docker-drawio)
- 历史 PM Runtime 的另一套项目/材料/六类 DSL 不是本次默认迁移对象。
- 不把仓库版本未提供的多人实时协作写进一期承诺。

## 被替代的计划

[旧路线](../ROADMAP.md) 中待执行的自研无限画布、线段编辑、容器拖拽等工作停止按原方式扩展，由新实施计划和 draw.io 原生能力承接。已完成能力、历史测试和原文件不删除。

## 改变本决定的条件

若复杂泳道、双向同步或后台交付无法通过明确的验证，记录复现、引擎版本、替代方案和产品影响，再新增 ADR。不能因为单次集成困难而未经记录恢复自研白板路线。
