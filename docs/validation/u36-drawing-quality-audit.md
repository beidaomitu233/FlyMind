# U36 本地与线上绘图质量全链路审计

日期：2026-10-27。状态：**审计完成，等待用户决定改进方向；本轮不修改绘图行为，不提交、不发布。**

用户没有可逐图比较的原始数据，明确描述四类问题：流程过长、节点逻辑性差、业务主线不清、颜色配色差。本报告区分代码/隔离复现的确定事实与对用户实际图的推断。

## 1. 结论

当前没有证据证明线上使用了一套不同的低质量布局引擎。确定的差异是：远程 MCP 交给 Agent 的初始化规则显著少于本地；确定的共同缺口是：内容质量不能评价业务正确性和表达粒度，纵向排版没有长流程表达策略，增量编辑存在重叠/样式退化，配色接口声明与实际入口不符，且没有强制的实际图片质量评审闭环。

因此，同一渲染器接收不同粒度/主次/关系的内容，或以不同的增量操作序列搭建图形，会得到差异很大的结果。上述机制已验证，但没有实际失败图及调用序列，不能认定它们各自解释了用户全部线上图。

## 3. 全链路发现

### 3.1 Agent规则分发：两端初始化上下文不等价

`server/mcp-native/server.ts:27`：本地初始化 instructions 直接包含 `nativeGuide`，实测4106字符；远程仅75字符，要求先读取 `get_drawing_guide`。完整规范在Agent主动调用后才取得。两端工具数均18个，工具描述和JSON schema完全一致，按kind读取后的标准版本、能力与流程样例一致。

`server/mcp-native/server.ts:92`：不带kind读取指南时，两端都没有具体类型样例；`create_diagram`也没有“已读当前规则”状态或准入前置。仓库 skill 另有先读指南、按类型取模板、校验warning和交付图片要求，但连接远程URL不会自动安装该客户端skill。

**影响：**远程新对话更依赖Agent主动获取和遵守规则；本地开发对话或客户端skill可能提供了额外上下文。这是确定的上下文差异，用户实际模型/上下文和是否读过规则尚无记录，不能称已证明唯一因果。

### 3.2 内容生成：服务端没有业务理解和改稿模型

MCP接收外部Agent编写的nodes/edges，再送共享服务；创建与修改参数不包含原始业务材料、目标受众、概览/详细粒度、业务主线等信息。`inspectDrawing(content)`也只接收内容图，无法核对“材料要求审批之后付款，而提交图是付款后审批”这样的来源约束。

`src/drawing/core/model.ts:1`及 `server/contracts.ts:7`：流程节点仅start/end/task/decision，边主要flow/feedback。多边可以表达依赖和分支，但没有显式主次路径、子流程或AND/OR汇合语义。复杂业务中哪些动作合并、哪些分支重要、是否并行，主要由Agent自行决定。

**影响：**节点名称短、图连通，不代表概括正确或业务主线清晰。对话里的“做个主流程”没有成为服务端可验证的表达目标。

### 3.3 内容准入：存在真实约束，但机器分不是综合质量分

`src/drawing/core/drawing-quality.ts`确实检查类型字段、文字预算、判断出口、连通、入口可达与结果路径等；不能称它完全没有业务规则。然而，它不验证原始材料事实、重复流程动作、概览节点数量、粒度一致、关键路径、配色或完整可读性。

确定复现：

| 合成输入 | 实际返回 |
|---|---|
| 40个重复“处理”task，正常串链，红绿交替填色 | score=100，passed=true，issues=[] |
| 40个均超过建议长度但未超硬上限的标题 | 40条wordy_label警告，score=80，passed=true |

`drawing-quality.ts:108–109`将warning总扣分封顶20，无error时无论warning多少都不会低于80；新建准入只检查passed。因此“80/100分合格”不能保障用户看到的专业水平。

### 3.4 首次布局：流程默认纵向，没有概览或长链表达门槛

`src/drawing/engine/drawio/generic.ts:46–50`：流程/数据流默认纵向；只有脑图在未指定方向时比较横竖的紧凑成本。ELK按既有边排序，不会决定哪些业务节点应合并或抽成子流程。节点和层间距有标准值，但没有对流程整体长宽比/阅读长度的强制门槛。

PM实际编译：

| 普通task数量（另有起终点） | 业务节点外包围宽×高 | 高宽比 | 内容分 / 布局问题 |
|---|---|---|---|
| 8 | 200×1566 | 7.83 | 100 / 无 |
| 20 | 200×3558 | 17.79 | 100 / 无 |
| 40 | 200×6878 | 34.39 | 100 / 无 |

`routing.ts:80–83`的长宽提示只覆盖特定过宽情形，且assert会过滤该提示；细长流程不被拒绝。feedback边在首次排序中排除，分类依赖Agent正确提供kind；内容校验不按“退回”文案自动补该语义。

**影响：**机械拆成许多步骤后，渲染器忠实排成长条；“无碰撞”与“便于理解”不是一回事。简单横竖切换也不会减少业务节点或建立主次。

### 3.5 增量搭建：已复现重叠和样式退化

`generic-patch.ts:24`按同parent的兄弟节点找末尾位置；新增未分组节点时，没有把已有组内节点与容器标题作为同一放置障碍集合。`:31`新增节点走通用配色；`:42`结束前检查路由、内容投影和锁，但没有与首次编译相同的全图布局阻断。

复现先创建两组Vue→Spring Boot技术图，再AI新增合法的未分组Redis：

- 创建/修改保存成功，内容quality仍100、issues为空。
- 新节点坐标 `(64,128,180,148)`，诊断出现 `NODE_OVERLAP` 和 `NODE_HEADER_OVERLAP`。
- 同一Redis首次完整编译是透明、深灰文字的技术组件；增量新增却是淡紫填充/紫边框的通用卡。
- 原节点几何确实保留，本地服务与隔离cloud的增量XML也相同。

**影响：**分几轮让AI搭建和修改，可能比一次完整生成更乱、更不统一。这是确定的产品缺陷，不是仅靠提示词能保证避免的问题；但该具体复现不是用户线上原图。

### 3.6 样式和配色：预设有限，修色入口存在接线缺口

- `model.ts:51–54`主要是blue/indigo/forest三套palette；普通节点多使用相同底色，判断用另一色，架构层按索引交替色。没有主次/角色/条件结果的统一语义色规则或对比度质量校验。
- `technical-layout.ts:9–11`固定蓝色虚线边框、红色组标题、深灰技术文字。这来自具体版式策略，不能理解为会根据任意业务自动选择合适配色。
- 技术布局按有限technology注册表识别客户端/网关/服务/存储/运维等类别；未知技术会按other和实际依赖深度回退。特定参考图的适配不证明所有陌生技术拓扑都有同等展示效果。
- `mcp-native/contracts.ts:13`向Agent暴露完整rendering变更schema；但真正经过的 `drawio/index.ts:215–218` 外层入口只允许orientation/relayout。内部 `configure.ts` 虽有颜色等实现，外层仍会拒绝这些字段。

PM实测theme、nodeDefaults、edgeDefaults、styles四类参数均通过MCP schema，却全部在引擎入口报 `UNSUPPORTED_RENDERING_OPTION`。因此Agent即使按声明调用配色工具，也可能无法完成。两端共同存在，不能说只有云端如此。

### 3.7 原生渲染与导出：忠实输出，不会补业务逻辑

NativeDrawioRenderer加载已保存的XML，检查字体供应、资源安全、原生加载前后签名、PNG尺寸等，再交制品。没有服务端视觉模型评审或自动改稿。MCP等待任务、校PNG签名尺寸后直接返回图片，不强制Agent看图并修订。

超大图会按16384边长/32M像素等预算等比例缩小，可能进一步降低长图的总览可读性，但它不重写节点文字或先后关系。现无同图同修订的跨平台PNG差异证据，不能将四类症状归咎于Linux字体/图片压缩。

### 3.8 版本与追溯：仍有未能核实的部分

应用和MCP网关部署位置独立。日常应用晋级切换 `/opt/flymind/current`，网关使用独立固定目录；应用readyz的新release不能独自证明当前线上网关schema也已经更新。网关获取完整guide时会访问当前应用。本轮未调用生产授权MCP工具，因此网关实际初始化/tool版本仍需另行核对。

已有操作记录保存用户/团队/channel/clientId与实际修订delta，不保存Agent模型、原始任务、读取的规则版本、审图结论。导出制品的release/snapshot校验能追溯渲染供应，不能证明内容经过了专业审稿。

## 4. 本地/云端一致性对照

独立临时SQLite，分别走本地NativeDiagramService与真实隔离cloud HTTP AI创建路径。对比完整XML，覆盖几何、样式、归属和连线，不只对比内容hash：

| 输入 | 节点 / 边 / 组 | 完整XML |
|---|---|---|
| 六种类型最小合法样本 | 每例2–3节点 | 全部逐字节相同 |
| 完整技术参考图 | 24 / 14 / 9 | 逐字节相同，布局诊断无问题 |
| 含判断、分支、feedback的流程 | 24 / 24 / 0 | 逐字节相同，布局诊断无问题 |
| 技术图AI增量新增Redis | 两端同操作 | 逐字节相同；同样出现上述缺陷 |

这是当前同源码路径的对照，不等于对用户两次实际Agent输出、历史本机常驻Runtime或生产PNG逐张做过比对。

## 5. 为什么先前测试没有挡住

候选发布测试主要证明API、鉴权、保存/冲突、内容往返、固定样例的原生渲染和可交付；没有将“从同一份业务材料经Agent生成，再按业务结构/简洁/闭环/视觉/修改准确逐项评审”作为持续发布门槛。

仓库 `docs/validation/QUALITY_EVALUATION_PLAN.md:3`明确15例评测仍停留在输入/预期冻结，没有逐例生成评分证据；不能用机器分或接口测试数量代替该质量验收。之前对技术链路的验收范围不足以支持“线上生成水平与本地稳定一致”的承诺。
