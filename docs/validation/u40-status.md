## 已有证据

- 旧版云启动会让 Chromium 空闲常驻；候选启动验证后释放，导出后5秒空闲回收，并对超时清理失败做隔离。此前同工况 Windows 组件样本的空闲 Chromium 由约132 MiB 降至0；真实 Linux 卡死进程未复现。
- 修复导出超时/取消后的队列竞态：失败状态先持久化，旧 pipeline 未结束前保留队列占位，避免同一云 pool 跨团队或同一本地 worker 提前开始下一次渲染。renderer 另提供按次内部 quiescence 句柄，等待被 Promise.race 遗弃的工作、字体封装子进程 close 及相关 context 清理；清理不可确认时锁存 `EXPORT_CLEANUP_UNCERTAIN` 并停止队列。未决 release 配置等待可响应取消；维护排空仍有超时，关闭尝试清理各 worker 与共享 renderer。定向测试 65/65、服务端 TypeScript 检查及后续完整内存回归 182/182 通过；若工作永不结束，队列保持阻塞而非冒险重叠。该屏障不能约束其他进程或不同数据根，也不证明操作系统所有子进程均已退出。
- 本地和云端的清理故障锁存均接入导出入队事务：正常认证、身份/恢复纪元、幂等冲突和已有合法重放仍按原顺序处理；需要新 INSERT 时再次检查故障，避免故障发生在请求准备期间导致永久排队。云端在读取权限/团队身份检查后处理故障中的合法重放，继续保留正常容量和维护保护，并同步观察 worker 锁存以覆盖事件循环重入窗口；现有 queued 不自动删除。导出清理故障时 `/readyz` 显示 503 和稳定错误码，`/healthz` 仍表示进程存活；已授权读与合法重放保持可用。本地专项 3/3、云端故障和容量定向 2/2、故障就绪和维护定向 2/2、含真实浏览器但未测内存的云 HTTP 13/13 通过；进程重启后的故障状态持久化和跨进程隔离仍未证明。

## 发布前尚需完成

补充离线 Linux 环境准备：从带 SHA-256 清单的历史交付包中逐文件核验并提取固定浏览器和 Linux 依赖到新的隔离测试目录，使用独立的官方 Ubuntu 软件包补充浏览器动态库；未访问生产数据。Chromium 151 在无网络、非 root、256 MiB 限额的短时容器内已成功打开简单页面，没有传入 `--no-sandbox`。该容器使用 Playwright 1.62.1 的 seccomp 配置，并在去除全部能力后仅加入 `SYS_CHROOT`，以允许 Chromium 在用户命名空间建立沙箱；这改变了测试容器能力边界，不代表生产容器配置或生产安全已验证。浏览器烟测没有运行 FlyMind 渲染器，也没有证明完整应用的内存或图片质量。

首次真实渲染探针以 640 MiB、无交换、仅回环网络运行小图时，渲染前 cgroup 为 180,768,768 字节、Node RSS 为 169,541,632 字节；原有 512 MiB 可用内存准入拒绝了请求（`RENDER_MEMORY_LOW`），浏览器尚未启动、无 cgroup OOM。该次探针在渲染主进程中直接编译合成图，而产品创建路径将编译放在独立重活子进程，因此这次失败反映的是较重测试负载，不能认定等同生产冷渲染；下一步必须分别测试分进程编译及完整服务。未降低内存准入。

分进程生成合成 project 后，640 MiB 容器中的小图仍因渲染前约 162 MiB cgroup 占用被相同门槛拒绝。改用 704 MiB 容器、其他条件相同后，真实 Chromium 启动，但 cgroup 峰值达到上限 704 MiB，发生 `oom_kill=1`，最终 `RENDER_TIMEOUT`，未产出可验收图形。此实验不含真实云服务、数据库、MCP、Java 和宿主 WSL 开销，也不能归因于某个具体浏览器子进程或声称生产 OOM 的原因。容器使用测试专用 Playwright seccomp 和 `SYS_CHROOT` 能力；未关闭 Chromium 沙箱、未降低生产准入。当前不能认为 800 MiB 目标已达到，不能发布。

为定位启动后增长，使用单独的 Python 监督器在另一 704 MiB 无交换测试容器运行小图，约 560 MiB 时请求取消；采样非原子、阈值并非硬上限，实际 cgroup 峰值 591,200,256 字节（约 564 MiB），没有 OOM，独立 PID namespace 的测试进程已退出。水位附近 Chromium renderer 的 `/proc` RSS 约 272 MiB（其中匿名内存约 190 MiB），同期 cgroup 文件缓存约 193 MiB；不同进程 RSS 中共享页不可直接相加。这次使用 Python Debian 镜像并补充 Ubuntu 浏览器依赖，额外允许测试监督器使用 `pidfd_open`/`pidfd_send_signal`；镜像与先前 OOM 测试不同，且主动取消没有生成图片，不能当作可用性或图形输出验收。Chrome 页进程增长与文件缓存是测得的现象，不等于已确定代码级根因。

单独试验固定 draw.io `viewer-static`：在同一类 704 MiB 限制和 560 MiB 监督水位下，固定两节点合成图完成 viewer 初始化、进入 SVG 与 PNG 阶段，但在 PNG 完成前触发外部监督取消，峰值约 566 MiB、无 OOM、容器进程清理通过。该组件路径并非现有产品，SVG 未做离线字体封装，不能证明结果、功能或质量等价，也不能作为新渲染方案上线。viewer 默认网络资源路径须预先改为本地并拦截外联；含公式、HTML、图标及人工样式的用户图尚未覆盖。

同一 viewer 的另一隔离试验，改为对合成 SVG 页面截图而不使用原生 canvas 编码：没有触发 560 MiB 看门狗，cgroup 峰值 494,460,928 字节（约 472 MiB），无 OOM 且容器进程清理核验通过；生成 398×82、6,107 字节 PNG，已人工查看两个中文节点。样本没有连线，不是当前产品输出，未验证像素、字体嵌入、缩放、裁剪、背景、离线 SVG 或任意复杂图形；PNG 的视觉检查不代表等价。这里的峰值包含独立监督器而不包含完整云服务和宿主开销，两次组件实验并非完整产品的性能对照，不得用于宣称整机节省或上线。

更正方框范围：人工复查发现节点与连线中文可读，标题中的部分字形显示为方框，并非所有中文异常。后续在同等隔离条件下记录 canvas 实际使用的 SVG：5 个字体规则均为嵌入 data URI，解码 SHA 与选定的 5 个分片一致；页面逐字符普通和粗体 FontFace 加载检查均通过，输出 PNG SHA 与上述异常样本一致。此证据排除了该次字体数据未嵌入或与清单不符，并不能证明 SVG Image 的字形选择和异步解码正常；问题未修复，仍不能用于产品。

离线 SVG 在 Linux 以 `<img>` 加载的补充实验：对 SHA 固定的同一图形，分别以 5 个 WOFF2 分片和完整 OTF 生成的 SVG 运行。容器以单独配置禁用系统字体源，fontconfig 逐一确认样本 15 个汉字没有匹配的已注册系统字体；无网络、相同浏览器与图形尺寸。两种 `<img>` 截图 SHA 完全一致，人工查看均看不到文字，分片与完整字体分别峰值约 346 / 511 MiB，均无 OOM 并完成进程清理。该结果显示至少在此 image 嵌入和空字体配置下，现有基线与候选都存在文字可用性问题，不能将其归因于分片，也不能仅凭先前 Windows 的像素一致记录判定 SVG 离线可用。系统字体配置是测试专用，未覆盖所有 SVG 查看方式；独立文档打开与等待字体加载仍需对照，问题未修复。

后续对照：分片 SVG `<img>` 等待 2 秒与 iframe 独立文档截图仍相同且无文字，iframe 中 5 个 FontFace 返回 `NetworkError`；只在 CDP 层拦截 HTTP(S)、放过 data 协议后现象不变。提取完全相同的字体 CSS 放入 HTML 后，data MIME 改写为 `application/font-woff2` 仍失败；将相同已校验字节改为本地 HTTP 也失败，部分 HTTP 响应已确认 200、长度与请求完成。然而另一 viewer probe 在同样空系统字体配置下以同源 HTTP 加载相同分片并正确显示，因此独立 probe 的服务、CSS 或浏览器执行方式仍可能存在差异，尚不能将空白作为确定的产品缺陷或具体根因。完整 OTF 的 iframe 对照因保护水位中止，未产生结果。全部为隔离测试，未更改正式字体策略。

进一步校验发现，浏览器收到的 5 个 WOFF2 的长度和 SHA 均正确，直接使用二进制 `FontFace` 均可加载；页面中实际 CSS 内容也与服务器发送的 SHA 一致。将同一 HTTP 字体 CSS 从随 HTML 解析改为页面加载后插入，并先等待普通/粗体字体再显示文字后，5 个字体面全部加载且中文可见；原始时序仍失败。实验还改变了文字显示和等待的时机，不能证明唯一根因，更不能直接推断无脚本 SVG 的处理方式；所观察文字缺失及分片兼容性仍须解决或可靠回退。

后续补充：页面就绪后插入的原始 `data:font/woff2` CSS 亦能加载全部 5 面，截图与同条件本地 HTTP 字体完全一致。将文档响应从分块改为相同内容的一次性响应不能恢复字体；取消 Playwright/CDP 请求拦截、仅在专用无外网容器中被动观察，SVG 独立文档与 HTML 的原始时序仍失败。固定 SVG 内存副本为每条 `@font-face` 加 `font-display:block` 也未恢复。失败条件与 viewer 成功路径之间仍有其他差异，以上不能证明具体 Chromium 缺陷或生产影响；不应上线未经跨平台真实查看与回退验证的分片方案。
