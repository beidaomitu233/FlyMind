# U40 服务器存储：调查和本地验收

状态：本地开发中，尚未部署；用户正在处理原服务器，本批不连接、删除或重启线上资源。

## 证据与范围

用户截图显示 `/var/lib/flymind/production/control-plane-deployments` 约 6.0 GiB、`/opt/flymind/releases` 约 5.3 GiB。父目录数字已包含子目录，不能相加推算总量。截图没有提供文件清单，不能断言两项分别包含哪些具体文件或可安全回收多少。

代码证据：控制面每次尝试保留一份下载归档、完整展开候选（包括应用资源与 Java JAR）、上版 JAR 和回执；成功后原代码没有清理候选。应用 release 每次物化完整文件树；compact 只减小传输包，并非自动共享磁盘数据。应用离线备份含数据根，MySQL 备份另存，不属于部署临时文件。

独立复核还确认不同 release 即使 JAR 字节相同，也会各自保留 `previous.jar`；因此长期 JAR 副本会继续增长，但截图并不能证明其在6.0 GiB中的实际比例。历史 JAR 与旧数据库备份可能需要配对做人工恢复，已成功运行也不代表它兼容当前数据库；本批不按时间自动删除这些文件。限量删除会降低历史恢复能力，需要另行形成可审计策略。

本机旧 Windows 交付样本 `output/v11-deployable-win32/application` 的资源为约 438 MiB、依赖约 186 MiB；其中浏览器约 274 MiB、draw.io 约 148 MiB。它只是本机旧样本，不是 Linux 服务器当前目录清单。服务所需浏览器、图形资源、字体和依赖不能简单删除。

## 本地候选

1. Java 控制面成功后只清理**本次**确认成功的候选展开树和归档。校验受保护根路径、持锁、结果回执、启动意图、运行 JAR 摘要、设备与挂载点，失败和状态不明时跳过；保留 attempt 目录、结果、`previous.jar`、备份与迁移幂等证据。清理失败不会伪造部署失败；幂等成功重放可再次尝试清理。
2. compact 物化不变的可重建发布文件时优先尝试文件系统写时复制；不支持时退回独立普通文件，不用硬链接，保留摘要验证和独立 inode。能否节省物理空间取决于目标文件系统支持，不能假定所有服务器均生效。用户 dataRoot 发布前备份不主动请求写时复制，仍为普通复制；但文件系统或存储层可能透明去重，同机普通复制也不是独立故障域，需要另有经过校验的异机或离线备份。
3. 增加只读版本清点与审查计划，见 [使用说明](../cloud/RELEASE_INVENTORY.md)。缺少应用 current、网关引用、回滚、未完成/不确定的发布或引擎供应等证据时保留全部版本；即使证据齐全也不会自动删除。现有代码中应用回滚失败仍可能释放部署锁，不能把“没有锁”当成无风险证据。
4. 发布包构建和逐文件验证改用流式 SHA，不再把浏览器或 JAR 整个读进 Node Buffer；完整文件大小、摘要和清单校验仍保留。实际部署使用的受限静态验证器必须单独更新并核对固定哈希，不能假设源码改动已自动替换它。
5. 修复 SVG 字体挑选对 `justify-content` 的误判：仅当整个 inline flex 声明符合保守白名单时才使用固定字形分片，复杂或未知文字、样式仍使用完整字体。固定小图隔离实验中 SVG 从 21,922,667 B 降至 675,170 B，约减少 96.9%；固定复杂技术图从 22,006,602 B 降至 1,827,882 B，约减少 91.7%。这是两份合成样本，其他图形及旧存量文件的实际节省尚未测量，且不会自动重写已有导出。

## 历史版本去重与物化峰值复核

历史应用版本可能仍被当前应用、网关、回滚、增量包基线或未完成导出引用；现有回执和各空间队列不足以证明所有引用已解除，也不能假定保留 30 天的远程构建制品可长期重建。因此不按数量删除历史版本，或把未知版本当作可回收空间。成功控制面部署的本次临时清理不等于历史版本已被清理。

不支持写时复制的文件系统会将不变文件重新复制，长期版本占用仍待解决。将历史版本文件硬链接到新版本会共享可变 inode，单凭摘要相同和当前权限无法保证将来的 root 维护不会修改历史版本，不能作为安全去重方案。正在评估只移动本次私有解压目录中的文件以减少部署过程的临时双份占用；这不能减少历史版本的长期占用，也不能替代对回滚和备份策略的完整设计。

审计时发现，原应用发布器在命令超时发送终止信号后即返回错误，原控制面发布器在超时或输出超限时也会先发送终止信号并返回，两者均未保证等待子进程实际 `close`。本地候选已增加有界退出确认；子进程或 systemd 状态不确定、回滚失败、回执无法确认时保留锁和现场，pending 和恢复标记阻止跨发布编号重试。具体恢复约束见 [发布中断与回执恢复](../cloud/DEPLOYMENT_RECOVERY.md)。这项源码风险未证实曾导致线上故障，批量转移方案仍未接入。

PM 在无网络、256 MiB 无交换的非 root Linux 容器中独立运行发布生命周期和既有控制面、清理、compact、部署测试：首次 47/48，唯一失败是镜像没有测试写死的 `/usr/bin/python3`；随后仅在容器临时目录补齐指向镜像自身 Python 的路径，重跑 **48/48 通过**，含 Linux 真符号链接。测试采用临时文件、微型子进程和 fake systemd，并非 root 发布器、真实 systemd、断电或生产挂载测试。Windows 隔离回归另为 29 通过、1 个 Linux 专项跳过；更早受限沙箱权限失败的日志保留。静态发布器仍固定旧来源，不代表服务器已经安装新逻辑。
